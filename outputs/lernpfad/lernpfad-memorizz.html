Kapitel 1 — Orientierung

1.1 Das Problem, das memorizz löst

Ein Sprachmodell hat kein Gedächtnis. Jeder Aufruf beginnt bei null; alles, was das Modell „wissen“ soll, muss in dieser einen Anfrage im Kontextfenster stehen. Das hat drei praktische Folgen:

  • Vergessen. Was der Nutzer gestern gesagt hat, was ein Tool letzte Woche ergab, welche Vorgehensweise schon einmal funktioniert hat — weg, sobald die Session endet.
  • Kosten und Grenzen. Alles in den Prompt zu stopfen ist teuer (Tokens) und stößt schnell an das Kontextfenster.
  • Falsche Erinnerung. Wer naiv „alles Ähnliche“ aus einer Vektor-Datenbank in den Prompt kippt, bekommt Dubletten, Widersprüche und veraltete Fakten.

Klassisches RAG (Dokumente einbetten, ähnliche Passagen suchen) löst nur einen Teil davon: das Faktenwissen. Ein Agent braucht aber mehrere Arten von Gedächtnis — und genau das ist die Grundidee von memorizz: Gedächtnis nach kognitiver Rolle trennen, so wie man es aus der Kognitionspsychologie kennt.

1.2 Was memorizz ist — und was es dir bringt

In einem Satz: memorizz ist ein Python-Framework für „memory-augmented“ KI-Agenten — es liefert die Gedächtnis-Systeme, die Speicherung dahinter, eine Agenten-Laufzeit, die damit arbeitet, und fertige Oberflächen (Terminal-CLI, Web-UI, MCP-Server). Konkret bekommst du:

  • Persistenz über Sessions hinweg — agent.run("Ich heiße Leah …"), Prozess beenden, neu starten, agent.run("Was weißt du über meine Arbeit?") funktioniert.
  • Semantische Suche — Erinnerungen werden als Vektoren (Embeddings) abgelegt und nach Bedeutung, nicht nach Stichwort gefunden.
  • Austauschbare Speicher — derselbe Agent-Code läuft auf Dateisystem (lokal, mit FAISS), MongoDB oder Oracle. Für den Einstieg brauchst du keine Datenbank.
  • Werkzeuge mit Leitplanken — Python-Funktionen werden automatisch zu Tools; riskante Aktionen (Browser, Code-Ausführung, MCP-Mutationen) brauchen eine dauerhafte Freigabe durch den Host.
  • Mandantenfähigkeit — ein Agent, viele Endnutzer, sauber getrennt über user_id.
  • Sparsamer Kontext — Deduplizierung, Zusammenfassungen, Semantic Cache und prompt-cache-freundlicher Aufbau halten Token-Kosten klein.
  • Sofort benutzbar — pip install memorizz und memorizz im Terminal startet einen Claude-Code-ähnlichen Agenten mit Gedächtnis; mit laufendem Ollama sogar komplett ohne API-Key.
Ehrliche Einordnung

Das README nennt memorizz ausdrücklich experimentell/educational: APIs können sich ändern, es gab kein Security-Hardening für Produktion. Und: Die Lizenz ist PolyForm Noncommercial 1.0.0 — Nutzung nur nicht-kommerziell (siehe LICENSE, NOTICE). Beides gehört zu „was es bringt“: hervorragend zum Lernen, Prototypen und Forschen; für ein kommerzielles Produkt brauchst du eine andere Lizenzgrundlage.

1.3 Das mentale Modell: drei Säulen + zwei Anbauten

Wenn du nur eine Sache aus diesem Kapitel mitnimmst, dann dieses Bild:

Die Laufzeit (C) benutzt die Memory-Systeme (A); die wissen nichts über Datenbanken, sondern reden nur mit dem MemoryProvider-Interface (B). Deshalb kannst du das Backend tauschen, ohne Agent- oder Memory-Logik anzufassen.
Säule A
Memory-Systeme — src/memorizz/long_term/, short_term_memory/, coordination/. Fachlogik: was ist eine Persona, wie wird eine Wissensbasis in Chunks zerlegt, wann wird zusammengefasst.
Säule B
Storage-Provider — src/memorizz/memory_provider/. Ein abstraktes Interface (base.py: store, retrieve_by_query, retrieve_by_id, list_all, update_by_id, delete_*, …) und drei Implementierungen.
Säule C
Agent-Laufzeit — src/memorizz/memagent/. MemAgent (core.py, 6 900 Zeilen — das Herz), MemAgentBuilder, elf Manager (Memory, Tool, Cache, Persona, …), Orchestratoren.
Anbau 1
Modelle — llms/ (OpenAI, Anthropic, Azure, Ollama, HuggingFace, MLX) und embeddings/ (OpenAI, Azure, Ollama, HuggingFace, VoyageAI).
Anbau 2
Fähigkeiten — Internetzugang, Sandbox-Codeausführung, Browser-Steuerung, MCP-Client, Skills-Marktplatz, Automationen. Jede Fähigkeit hängt sich als Tool-Satz an den Agenten; keine ersetzt das Memory-Modell.

1.4 Ein erster Blick auf Code: der Quickstart, Zeile für Zeile

Das ist der Einstieg aus dem README (README.md:85–122). Lies ihn einmal mit dem Drei-Säulen-Bild im Kopf:

1from memorizz.memagent.builders import MemAgentBuilder          # Säule C
2from memorizz.memory_provider import FileSystemConfig, FileSystemProvider  # Säule B
3
4provider = FileSystemProvider(FileSystemConfig(
5    root_path=Path("~/.memorizz").expanduser(),      # wohin: lokaler Ordner
6    embedding_provider="openai",                       # Anbau 1: wer macht Vektoren
7    embedding_config={"model": "text-embedding-3-small"},
8))
9
10agent = (
11    MemAgentBuilder()
12    .with_instruction("You are a helpful assistant with persistent memory.")
13    .with_memory_provider(provider)                    # C bekommt B
14    .with_llm_config({"provider": "openai", "model": "gpt-4o-mini", "api_key": …})  # Anbau 1
15    .with_semantic_cache(enabled=True, threshold=0.85)  # Säule A: Kurzzeit-Cache
16    .build()
17)
18
19print(agent.run("Hi, my name is Leah and I work on payments systems."))
20print(agent.run("What did I tell you about my work?"))   # Antwort kommt aus dem Gedächtnis
21print(agent.get_context_window_stats())               # Token-Statistik des letzten Turns

Drei Beobachtungen, die später wichtig werden:

  • Der Provider bekommt die Embedding-Konfiguration, nicht der Agent — denn Vektoren entstehen dort, wo gespeichert und gesucht wird.
  • Ohne .with_application_mode(...) gilt der Standard ASSISTANT (enums/application_mode.py:23). Der Modus entscheidet, welche Memory-Typen aktiv sind — Zeile 33–56 derselben Datei ist die Tabelle dazu.
  • agent.run() gibt einfach einen String zurück. Alles Interessante (Abruf, Dedup, Speichern) passiert dahinter — das ist Kapitel 2.

1.5 Das Vokabular: MemoryType, ApplicationMode, die drei IDs

MemoryType (src/memorizz/enums/memory_type.py:31–46) zählt die 13 Speicher-„Fächer“ auf: KNOWLEDGE_BASE, PERSONAS, ENTITY_MEMORY, TOOLBOX, WORKFLOW_MEMORY, SKILLBOX, CONVERSATION_MEMORY, SUMMARIES, SHORT_TERM_MEMORY, SEMANTIC_CACHE, TOOL_LOG, SHARED_MEMORY, MEMAGENT. Jedes Fach ist beim Provider eine eigene Sammlung (Collection/Tabelle/Ordner). Nettes Detail: die Datei akzeptiert noch den alten Namen LONG_TERM_MEMORY für KNOWLEDGE_BASE, damit alte Datensätze weiter laden — ein Hinweis darauf, dass hier auf Abwärtskompatibilität geachtet wird.

ApplicationMode (enums/application_mode.py) sind Voreinstellungen, welche Fächer ein Agent benutzt:

ModusAktive Memory-TypenGedacht für
assistant (Standard)conversation_memory · knowledge_base · personas · entity_memory · short_term_memory · summariesPersistenter Gesprächsassistent mit Personalisierung
workflowworkflow_memory · toolbox · knowledge_base · short_term_memory · summariesStrukturierte Aufgaben-/Tool-Pipelines
deep_researchtoolbox · shared_memory · knowledge_base · short_term_memory · summariesRecherche mit mehreren kooperierenden Agenten

Die drei IDs. memorizz adressiert Gedächtnis hierarchisch (docs/guides/multi-tenant.md:8): user_id → agent_id → memory_id → thread_id. user_id ist die Mandantengrenze (wird bei jedem Lesen/Schreiben erzwungen), agent_id identifiziert den gespeicherten Agenten, memory_id einen Gedächtnisraum innerhalb des Agenten, thread_id einen Gesprächsfaden. Alle sind Parameter von agent.run() (memagent/core.py:3252–3260) — also pro Aufruf wählbar, nicht fest verdrahtet.

1.6 Was bei agent.run() passiert — der Überblick

Die Architektur-Notiz des Projekts (src/memorizz/MEMORY_ARCHITECTURE.md:89–96) beschreibt den Ablauf so — Kapitel 2 folgt ihm dann durch den Code:

  1. memory_id / thread_id (und user_id-Scope) auflösen
  2. Semantic Cache prüfen — bei Treffer sofort antworten, ohne LLM
  3. Aktive Erinnerungen abrufen, deduplizieren (exakter Hash, Kosinus ≥ 0,95, gegen die Historie), per MMR auswählen und in einen prompt-cache-freundlichen Kontext bauen
  4. LLM/Tool-Schleife ausführen (Tools kommen aus Toolbox + Fähigkeiten; heikle Tools warten auf Freigabe)
  5. Nutzer- und Assistentenbeitrag persistieren
  6. Kontextfenster-Statistik und Zusammenfassungs-Registry aktualisieren

Merke — Kapitel 1 in fünf Sätzen
  1. LLMs vergessen alles; memorizz gibt Agenten ein Gedächtnis, das nach kognitiver Rolle getrennt ist (semantisch, prozedural, episodisch, kurzfristig, geteilt).
  2. Drei Säulen: Memory-Systeme (was), Storage-Provider (wo/wie), Agent-Laufzeit (wer) — plus Modell-Adapter und optionale Fähigkeiten.
  3. Die Fachlogik redet nur mit dem MemoryProvider-Interface; darum ist das Backend austauschbar.
  4. MemoryType (13 Fächer) und ApplicationMode (3 Voreinstellungen) sind das Vokabular; user_id → agent_id → memory_id → thread_id die Adressierung.
  5. Experimentell, nicht-kommerzielle Lizenz, sehr junge Codebasis — ideal zum Lernen und Prototypen.
Kontrollfragen (beantworte sie im Chat — ich gebe Feedback)
  1. Warum trennt memorizz die Memory-Systeme (Säule A) von den Storage-Providern (Säule B)? Was ginge kaputt, wenn KnowledgeBase direkt MongoDB-Aufrufe enthielte?
  2. Der assistant-Modus aktiviert personas und entity_memory, der workflow-Modus nicht — aber toolbox. Was sagt das über die beiden Einsatzzwecke?
  3. Zwei Endnutzer deiner App reden mit demselben Agenten. Welche ID hält ihre Erinnerungen auseinander — und warum ist es ein Parameter von run() und nicht des Builders?

Glossar
Agent
Programm, das ein LLM in einer Schleife mit Werkzeugen und Gedächtnis betreibt, bis eine Aufgabe erledigt ist.
MemAgent
Die zentrale Klasse von memorizz (memagent/core.py); koordiniert Memory, Tools und Modelle über Manager.
MemoryProvider
Abstraktes Speicher-Interface; Implementierungen: Filesystem, MongoDB, Oracle.
MemoryType
Enum der 13 Speicher-Fächer (Wissensbasis, Persona, Toolbox, Konversation, …).
ApplicationMode
Voreinstellung, welche Fächer aktiv sind: assistant, workflow, deep_research.
Embedding
Zahlenvektor, der die Bedeutung eines Textes kodiert; ähnliche Bedeutung → nahe Vektoren.
Vektorsuche
Suche nach den Vektoren mit der größten Ähnlichkeit (z. B. Kosinus) zur Anfrage.
Semantic Cache
Kurzzeit-Cache: kommt eine sehr ähnliche Frage erneut, wird die gespeicherte Antwort geliefert.
Kontextfenster
Maximale Tokenmenge, die ein LLM pro Anfrage sieht — der knappe, teure Platz.
Tool
Funktion, die das LLM aufrufen darf (Web-Suche, Code ausführen, Datei lesen …).
MCP
Model Context Protocol — Standard, um Tools/Ressourcen zwischen Hosts und Servern auszutauschen; memorizz ist Client und Server.
user_id / memory_id / thread_id
Mandant → Gedächtnisraum → Gesprächsfaden; Parameter von run().
